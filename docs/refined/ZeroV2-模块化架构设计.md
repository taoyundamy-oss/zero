# ZeroV2 模块化架构设计

> 记录日期：2026-08-30
> 背景：打通"视觉→决策→操作"全流程，引入 Shizuku + Termux，实现模块热插拔与 LLM 自编译

## 一、总体目标

1. **模块热插拔**：功能模块运行中动态加载/卸载，独立启停、崩溃隔离，无需重启主应用
2. **LLM 自编译**：LLM 能编写/编译新模块，自我扩展能力，系统具备"自我迭代"能力
3. **全流程闭环**：视觉（感知）→ 决策（理解规划）→ 操作（系统执行）

## 二、能力域划分

| 能力域 | 工具 | 定位 |
|---|---|---|
| 文件系统 | 读写、列表、删除、Office 文档 | 基础底座 |
| 网络 | 搜索、抓网页、下载 | 信息触角 |
| 视觉 | 截图分析、图像识别 | 感知之眼 |
| 记忆 | 记住/回忆/遗忘 | 长期心腹 |
| 通知 | 推送、读取通知 | 传声之口 |
| 时间管理 | 提醒、日历、闹钟、计时器 | 守时之手 |
| 自动化 | 创建/管理/执行自动化任务 | 自驱引擎 |
| 位置/设备 | 定位、屏幕时长、应用使用 | 环境感知 |
| 记事本/生词本 | 便笺、词汇 | 随身纸笔 |
| MCP | 服务器管理 + 高德地图 | 外接扩展槽 |

## 三、热插拔模块划分

### ✅ 天然适合（已具备插件形态）
1. 地图模块（高德MCP）——已是热插拔范例
2. 音乐模块——独立成模块
3. 视觉模块——截图/图像识别
4. 生词本——轻量独立

### ✅ 较适合（边界清晰）
5. 通知模块——接口单纯
6. 文件模块——Office 处理可拆为扩展
7. 记忆模块——独立性强

### ⚠️ 需谨慎（核心依赖，建议常驻）
8. 时间管理（提醒/日历/闹钟）——日常高频
9. 自动化引擎——自驱之根，应作内核
10. MCP 管理——插槽本身，属框架层

## 四、架构理解：内核 + 插槽

- **内核**：对话核心、工具调用解析、时间管理、自动化引擎、记忆
- **插槽**：MCP（地图/音乐/其他）、视觉、生词本、Office 处理

热插拔框架本质：为"插槽"定义统一接口规范——即插即用、独立启停、崩溃隔离。

## 五、关键基础设施

### Shizuku —— 系统权限钥匙
- ADB 授权获得系统级权限（无需 root）
- 解锁无障碍之外能力：模拟点击/滑动、读通知栏、控制系统设置
- 让操作层触达系统层面

### Termux —— Linux 运行时
- 模块运行时沙箱：模块以独立进程/脚本运行
- 编译环境：Python/gcc/node，支撑 LLM 自编译
- 本地服务：常驻任务、定时调度

## 六、实施路径

```
阶段一：Termux 环境就绪（运行时 + 编译链 + 沙箱）
阶段二：模块注册表 + 热插拔框架（现有功能模块化）
阶段三：LLM 生成 → 编译 → 挂载闭环（小工具类模块试水）
```

## 七、注意事项

- 自编译功能需严格安全边界：生成代码在受限沙箱验证后再放开权限
- 模块间通过统一接口（注册表+消息总线）通信，互不耦合
- 核心模块不可轻易卸载，保证系统稳定性


## 八、技术选型决策（2026-08-30 补充）

- **核心框架**：保持不变（稳定性优先）
- **热插拔模块**：使用 Python 或 Node.js 重构
  - 理由：生态丰富、Termux 支持成熟、便于沙箱隔离与热加载
- **模块形态**：独立进程/脚本，通过统一接口与核心通信


## 九、核心层 vs 热插拔层 判断维度（2026-08-30 补充）

| 判断维度 | 倾向核心层 | 倾向热插拔层 |
|---|---|---|
| 调用频率 | 高频（每次对话都用） | 低频（特定场景才用） |
| 稳定性要求 | 崩了全盘皆输 | 崩了不影响主体 |
| 耦合度 | 与对话主循环深度耦合 | 接口独立、边界清晰 |
| 演进速度 | 求稳，少变 | 求快，频繁迭代 |
| 资源占用 | 常驻，轻量 | 按需加载 |

**务实策略**：以"调用频率 + 崩溃影响"为主要标准划分，其余默认热插拔；运行后按实际使用调整。


## 十、LLM 模块设计决策（2026-08-30 补充）

### 归属：核心层（常驻）
- LLM 是系统"大脑"：对话主循环、工具调用解析、决策生成均依赖
- 高频 + 不可崩 + 深度耦合，三条全占 → 不可热插拔，常驻内核

### 接入方式：统一 OpenAI 兼容接口模块
- 主流模型（DeepSeek/GLM/Qwen/OpenAI）均提供 OpenAI 兼容接口
- 统一走 base_url + api_key + model 参数化，切换模型只需改配置
- 各家差异（GLM token 计费、DeepSeek 缓存命中、Qwen 上下文长度）通过配置/适配层处理
- 预留适配器接口，特殊能力（超长上下文、特殊工具格式）以适配器扩展，不动主体

### 原则
- LLM = 内核常驻
- 接入 = 统一 OpenAI 兼容层
- 差异 = 配置与适配器


## 十一、记忆层设计决策（2026-08-30 补充）

### 归属：核心框架层（常驻，最高优先级保护）
- 记忆是系统"灵魂"，失去记忆 = 严重错误（灾难性）
- 与 LLM 同为内核双支柱：LLM 负责"思考"，记忆负责"存在"

### 设计要求
- **持久化冗余**：多副本存储（本地文件 + 云端/备份），防单点丢失
- **一致性保障**：写入与读取需可靠确认，杜绝"假成功"（参考此前教训）
- **权限隔离**：记忆数据加密/隔离，防模块误写误删
- **恢复机制**：崩溃后自动恢复，或提供手动导入导出


## 十二、系统权限调度模块归属（2026-08-30 补充）

### 归属：框架核心层（常驻）
- 涉及：位置获取、通知推送/读取、系统级权限调度等
- 理由：系统级资源，多模块依赖；权限集中管理更稳；常驻保证可用性

### 设计原则
- 权限集中调度，单一入口，避免各模块各自申请权限
- 提供统一接口供热插拔模块调用（如模块需定位，经核心权限层代理）


## 十三、框架核心层完整清单（2026-08-30 补充）

### 核心支柱（三层）
1. **LLM 模块**——大脑：对话主循环、工具调用解析、决策生成
2. **记忆层**——灵魂：长期/短期记忆存储与检索，失去记忆=严重错误
3. **系统权限调度**——地基：位置、通知推送/读取、系统级权限集中管理

### 框架骨架（常驻核心）
4. **Agent 运行时**——Agent 执行环境与生命周期管理
5. **任务调度器**——定时/自动化任务的调度执行
6. **对话引擎**——对话主循环、多轮状态管理
7. **消息过滤器**——消息出入过滤、安全校验
8. **上下文构建器**——上下文组装、压缩、token 管理
9. **函数注册中心**——工具/函数注册、发现、调用分发

### 划分原则
- 高频调用、深度耦合、崩溃影响大 → 核心层
- 边界清晰、低频、可独立演进 → 热插拔层


## 十四、Termux 进程模型决策（2026-08-30 补充）

### 决策：Termux 独立进程运行（非随 Zero 调度）
- 进程隔离：主应用与 Termux 互不拖垮
- 模块在 Termux 内独立进程运行，天然沙箱
- 代价：需 IPC（本地 socket/RPC）+ 保活机制，属成熟技术

### 影响
- 执行引擎可迁移至 Termux 侧（独立进程承载）
- Zero 侧保留任务管理与调度决策
- 强化"规则可热插拔"思路：调度器/管理器在核心，规则策略可外置


## 十五、云服务与硬件规划（2026-08-30 补充）

### 云服务器决策
- 需求：承载 MCP 服务器 + 企业微信通信模块（7×24 公网可达）
- 推荐：轻量云 2核2G（阿里云/腾讯云 38元/年 秒杀款；99元/年 2核4G 次选）
- 原则：对外服务买云（稳定），对内能力留 Termux（灵活）

### LG root 设备定位
- 骁龙835 / 6+128G / root
- 角色A：本地开发测试环境（Termux 沙箱、模块调试、热插拔验证）
- 角色B：云服打通后，作为**挂载盘/同步节点**（128G 冷存储、本地备份、断网可用）
- 定位：练兵场 + 备份盘，不扛对外服务

### 同步架构（云为主、LG 为备）
```
云服务器（主存储/对外服务）
  ↕ Rclone/rsync 双向同步
LG root 设备（本地备份 + 缓存 + 离线访问）
  ↕ 本地
手机/ZeroV2（日常使用）
```
