## 2. 目标架构与模块职责

```text
UI / Automation / Trigger
  → TurnOrchestrator（单回合入口：权限、预算、取消、持久化）
    → ContextPlan（稳定前缀 + 历史窗口 + 本轮证据 + 风格）
    → ToolSelection（有界、确定性、可审计）
    → ModelRouter（需求能力 + 用户偏好 + 费用/可用性）
      → ProviderCodec（文本/图/音频内容块、流事件、usage）
    → ToolDispatcher（唯一安全执行入口）
    → Memory/Knowledge EvidenceProvider（只返回有引用的短证据）
```

模块目录只负责发现、元数据、状态和调用保护；ChatBot 不应同时负责图片理解、检索、角色评分、协议编码。新模块最短路径：实现模块自身能力 → 在 Hilt 集合注册 → 声明函数/权限/参数 schema/成本 → 通过注册校验 → 自动出现在模块中心及可选择的工具目录。具体样板和静态校验在实施计划 F1/F2 落地。所有外部模块调用保留 `ModuleLifecycleManager.safeCall()` 边界，Room 多步写入使用 `Mutex` 加事务；`MessagePipeline` 3 秒与 filter 100 ms 契约不变。

### 2.1 窄契约建议

在 `core:common` 放无 Android/Provider 依赖的 `ContentPart`、`ModelRequirements`、`EvidenceRef`、`PromptPlan`；在 `core:module-api` 放 `ModuleDescriptor` / 可选 `ToolContributor`；在 services 内实现 `ModelRouter`、`ProviderCodec`；框架 Chat 只依赖这些接口。不要把 Room Entity 当跨层 DTO。

```kotlin
sealed interface ContentPart {
    data class Text(val text: String) : ContentPart
    data class ImageRef(val attachmentId: String, val mime: String) : ContentPart
    data class AudioRef(val attachmentId: String, val mime: String) : ContentPart
    data class FileRef(val attachmentId: String, val mime: String) : ContentPart
}
data class ModelRequirements(
    val input: Set<InputModality>, val needsTools: Boolean,
    val needsStreaming: Boolean, val minContextTokens: Int
)
data class PromptPlan(
    val stablePrefix: String, val prefixVersion: String,
    val history: List<ChatMessage>, val turnContext: String?,
    val selectedTools: List<FunctionDefinition>
)
```

这是接口草案，不要求一次性替换 `ChatMessage` 或 `ILanguageModel`。先加适配器兼容旧序列化，验证单图、多图、纯文本与工具循环后再将新协议作为默认。所有模块新增/更名必须有 migration 或兼容映射、模块 ID 稳定、禁用状态可恢复。

## 3. 多模态成为聊天主路径

1. 输入层：`ChatMessage` 仍保存可读正文和附件元数据；`ContentPart` 给请求期内容表达。图片走 `content://` URI，复制到受控私有缓存/持久引用时做 MIME 嗅探、尺寸/像素/文件大小上限、EXIF 与隐私处理。不要把 base64 写 Room/Trace，也不要把完整图像长驻 `ChatHistory`。
2. 路由：根据本轮真实输入计算 `ModelRequirements`；按已验证 capability 选择 profile。文本维持用户首选，图片选图像输入模型；音频若 profile 支持原生音频才直送，否则复用 ASR→文本；输出 TTS 仍独立。原生失败时仅在可重试错误及用户配置允许时回退 Poke/ASR，不把协议 4xx 或超大文件无限重试。
3. 协议：`OpenAiCompatibleClient` 通过 provider codec 生成 text/image/audio 数组，协议不支持的内容块拒绝或显式回退。流解析继续沿用现有 tool call / reasoning 处理。`FunctionResult.data` 先保留文本供现有调用方；另加可选、限额的媒体结果引用，不直接把任意二进制塞工具回复。截图类工具以后才迁移。
4. 历史：UI 可复看附件；重发时检查 URI 授权/文件仍在，失败给可解释错误或回退已存文本摘要。摘要是替代旧历史的证据，不等同原图。工具及视觉结果与原输入用 attachmentId 关联，避免悄然改写用户原话。
5. 验收：纯文本请求序列化与既有快照等价；单/多图在支持 profile 出现原生 `image_url`；不支持 profile 有明确回退标签；图片失败不静默丢图；工具调用保持统一 Dispatcher；可追踪响应的 route、降级原因与大小，但不记私有媒体内容。

不默认下载 Qwen 本地多模态/embedding 权重。即使小参数模型也需要运行时、量化、内存、冷启动与发热测试；`Qwen3-Embedding-0.6B` 可作为后续研究候选，不是本轮随包依赖（[官方模型卡](https://huggingface.co/Qwen/Qwen3-Embedding-0.6B)）。

## 4. 稳定前缀、98% 缓存与上下文膨胀

### 4.1 请求布局

序列化顺序须由 provider codec 测试固定：`稳定系统前缀（基础安全/固定角色人设/版本化协议） → 已保留历史 → 本轮短上下文（摘要水印、证据、动态风格） → 当前用户内容块`。动态时间、亲密度、情绪、RAG、摘要、工具检索结果都不得写入稳定系统前缀。若 provider 将 `tools` 字段视为缓存前缀的一部分，工具列表必须稳定且排序确定；按需变更工具集的轮次单独成 cohort，不声称与前轮同前缀。角色编辑/切换、profile/模型/codec 变化必须更新 prefixVersion。

`prefixVersion = SHA-256(provider协议版本 | modelId | stableSystemBytes | toolManifestBytes)`；记录哈希、字节数、估算 token、服务商 hit/miss token，绝不记录完整 prompt 或 Key。DeepSeek 官方说明重复前缀缓存是 best effort，命中依赖服务端落盘/保存窗口（[官方规则](https://api-docs.deepseek.com/guides/kv_cache/)）。

### 4.2 指标与门槛

`eligibleStablePrefixTokens` 是同 provider/model/角色/prefixVersion 已有预热请求后，下一请求理论上可复用的稳定前缀 token；只在provider明确保证前缀命中且token边界可校准时计算 `min(reportedHitTokens, eligibleStablePrefixTokens) / eligibleStablePrefixTokens`。这是**稳定前缀代理指标**，provider usage 未给命中位置或系统token不可计数时只报估计值/unknown，不宣称精确system命中。主目标为固定cohort可观测热请求的token加权比率≥98%，同时报告P50/P10、样本数、覆盖率、全部input的cached比例。首轮和主动角色/模型/manifest变更单独分组；同cohort服务端失效、超时和零命中必须保留计数，不能挑选成功样本；缺usage单列且报告可观测覆盖率。服务商尽力而为导致目标不达时报告真实结果，不通过保留过长历史或改分母“刷指标”。

### 4.3 Token 和上下文治理

当前 `TokenBudgetAllocator` 主要为字符近似；加入 provider tokenizer 可用时的精确计数与保守误差系数回退。预算按模型真实 contextWindow - 输出预留 - 安全余量计算；稳定 system/核心工具先占位，再给最近历史、证据和动态风格设硬上限。推荐首期默认值（可配置并实测）：证据最多 3 条、每条 200–300 token，总计不超过可用输入预算 8%；动态风格 ≤120 token；摘要 ≤800 token；工具定义总额 ≤15%，不得截坏 JSON schema。长对话先利用 `summary_upto` 水印压缩旧历史，保留最近完整交互/工具闭环；绝不在用户消息中无来源地追加摘要。超预算按“低相关证据 → 旧工具结果 → 更早历史”顺序裁剪，必要时请求用户缩小文件。

工具扩张：固定小目录包含功能发现/调用的安全入口，意图匹配选 top K（首期 6–10，实测调整），允许用户明确要求时扩大。当前 `includeAllOperational=true` 只作迁移兼容，不能作为新默认。候选排序确定性、模块禁用/权限过滤、显式名称优先；无匹配时仅返回基础工具并提供发现工具，不全量回退。对工具说明压缩只在预先验证语义等价后实施。

## 5. 记忆与知识库升级

四种数据保持分离：`ConversationSummary` 用于历史压缩；`Memory` 是带来源、可撤销的用户事实/偏好；`UserGraph` 是当前用户状态的投影；`Knowledge` 是工作目录文档及 chunk。`EvidenceProvider` 只封装检索结果的短引用，不改变原所有权。

### 5.1 写入与纠错

- 对话结束后后台提取明确事实/偏好；来源 `messageId/attachmentId`、提取时间、置信度、模型版本、原文片段位置必须可追溯。AI 自述、推测、角色扮演内容、临时情绪不自动入长期记忆。
- 图/音频先转为可复核文本，候选需标记转写来源与不确定性；无可复核文本则不入库。
- 候选去重/冲突时优先保留新证据并标记旧条目 superseded，不静默覆盖。用户可查看、更正、删除，删除需级联清理 embedding/索引与派生证据引用。
- 将 `pendingAiBuffer` 改为有界 Room job/outbox：事务中写入任务与来源水印，唯一键避免重复；进程恢复续跑，失败退避；队列满时降级并留痕，不能无限增长。

### 5.2 检索与可扩展性

第一阶段只做有界候选：SQL 按 active/model/时间或词面预过滤、限制候选数，再对候选 embedding 余弦重排；Memory 与 KB 各自 DAO 维持索引与删除语义。中文沿用 LIKE/bigram 的有效行为，基于 100/1k/10k 条离线样本量延迟、内存、召回后决定倒排或 native vector 扩展。模型/维度不匹配继续降级纯词法，并展示重索引状态。不要假设 FTS5 默认 tokenizer 能提供足够中文召回。大规模数据确有需要时再做 sqlite-vec Android ABI/Room 接入 spike，必须有可关闭开关、降级查询和迁移回滚计划。

自动注入只取有来源的少量结果，结果按相关度、时效性、来源可靠性和重复性重排；同文档相邻 chunk 合并；低分数不注入。注入格式含类型、标题/时间、短摘录、来源 ID，模型回答可回链 UI。用户分别关闭 Memory / Knowledge 自动检索时，该源不参与请求，也不主动删除已有数据。

## 6. 动态角色机制

`CharacterEntity.systemPrompt` 保持固定可编辑人设；另建 `CharacterRelationState(characterId, affinityBand, counters, updatedAt, revision)` 和 `ConversationMoodState(conversationId, mood, intensity, expiresAt, revision)`，以及限量 `CharacterStateEvent`（来源消息、变化原因、幂等键、时间）。亲密度用**离散档位**而非伪精确“好感 73.42”；情绪如 neutral/warm/concerned/cheerful，短时衰减到 neutral。无状态记录视为默认值，便于迁移。

更新流程：用户/助手回合完成后由独立 `CharacterStateReducer` 读取可用文本证据，输出候选变化；确定性规则约束单轮最大变化、冷却、无关消息不变、负面/争执不自动惩罚用户。情绪由当前会话即时事件与用户显式设置驱动，有 TTL；亲密度按角色累积，并可在 UI 单独重置。任何评分不改变 SAFE/CONFIRM/FORBIDDEN、工具权限、事实来源、危机响应等固定规则，也不自动假设现实关系或要求用户维系亲密度。用户可在角色页看当前状态与最近变化依据、关闭动态表达、分别重置；角色删除时级联删除其状态。

Prompt 合成：固定人设留在 stablePrefix；短 style directive 放本轮可变上下文，例如“表达语气：温和，简短；保持既有事实与安全规则”，不暴露内部计分给模型。角色状态写入必须与会话事件形成事务/幂等关系，失败时以固定人设继续回复；状态 reducer 不占用 `MessagePipeline` 的 100 ms filter 路径。

## 7. 横切保障、指标与回滚

| 领域 | 最小证据 |
|---|---|
| 安全 | 所有工具经 `ToolDispatcher`；模块调用经 `safeCall()`；媒体 URL/URI 不允许任意服务器内网抓取；日志不含 Key/base64/个人证据正文 |
| 可靠性 | 单次附件/图片大小上限、解码采样、取消传播、请求超时；OOM/进程死亡后可恢复或给明确失败；Room 事务与 migration 验证 |
| 性能 | Z Fold3 目标上观察峰值 PSS、图片解码峰值、首 token 延迟、冷/热请求、检索 P95、DB 体积；12 GB 是整机 RAM，不能当应用可用内存 |
| 成本 | 记录每路由输入/输出/cached token 和媒体请求次数；超预算 fail clear；不为提升命中率重复上传全部历史 |
| 可观测 | Trace 只记录路线、前缀 hash、工具候选数量、证据 ID/数量、降级码、异常类型；UI 可诊断但不展示秘密 |
| 发布 | 每片有 feature flag / 旧路径回退；schema 前向迁移必须先验证，不能靠降版本回滚数据库；新 provider codec 可禁用 |
