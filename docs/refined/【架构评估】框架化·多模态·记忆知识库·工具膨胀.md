## 0. 总体判断

工程可继续增量开发，P1/P2 结构化推进的真实落地已被代码与测试证实（非虚标）。但当前阶段有一个结构性特征需要在进入 Feature 阶段前正视：

> **P1/P2 做的是在既有具体类"周围"加 seam 与测试，尚未重构核心接口本身。**

最难的几项——`IZeroModule` 接口宽度、`services → core:module-manager` 反向依赖、深模块协作者仍是具体类、契约测试覆盖——均显式推迟。这些债在纯文本对话 + 少量工具的现状下可承受；一旦多模态原生输入、工具目录扩张、记忆规模上涨三股力量同时进来，宽接口与字符串编排会反复逼你改所有模块。

本文给出四域的现状（代码证据）、问题与演进方向（带优先级），供后续设计 Agent 决策。

## 1. 框架化进展评估

### 1.1 已完成的地基（核实）

- `IZeroModule` / `ITimedModule` 抽象 + Hilt `@IntoSet` 自动收集（`app/di/AppBindingModule.kt`：31 个 `IZeroModule` 绑定 + `FunctionCatalog`/`ToolDispatcher`/`CredentialStore`/`ToolContextSelector` 4 个 seam 绑定）。
- `ModuleLifecycleManager` 统一生命周期：`safeCall` 包裹 configRestore/onAwake/onStart/onDestroy/reEnable；`runtimeStates` StateFlow；`getRuntimeState`/`isOperational` 执行前门禁；`initializeAll` 接入 `RegistrationValidator`（`core/module-manager/.../ModuleLifecycleManager.kt:68,84-107,136,222-226`）。
- 读写分离：`FunctionCatalog`（`getAllDefinitions`/`getEntriesByModule`）+ `ToolDispatcher`（`execute`/`executeBatch`），均由 `FunctionRegistryModule` 实现（`FunctionRegistryModule.kt:115,155`）。
- `FunctionCallIdentity` 调用身份贯穿（优先 `ToolCall.id`，空则 UUID，`traceId` 派生）；`executeBatch` 按 `dependsOn` 构建拓扑波次，缺失/歧义/环拒绝整批（`FunctionCallDag.kt`）。
- `CredentialStore` seam + `SecureKeyStore` 唯一实现；`RegistrationValidator` 启动校验；scope ownership（ChatBot/TriggerHub/SystemEvent/McpClient/AutonomousThinkingJob 的 destroy/close 均核实）；7 个大类内部策略 seam（TermuxCommand/TtsTextSegmenter/AutomationSchedulePolicy/FileFormatPolicy/MusicPlaybackPolicy/AutonomousTriggerPolicy/RelativePathPolicy）。
- 深模块雏形：`ChatBotModule` 隐藏 FC 循环/流式/世代压缩/最终综合；`MemoryModule` 隐藏分层/混合检索/写锁/冲突；`WorkDirRepository` 隐藏 SAF；`TermuxBridge` 隐藏 RUN_COMMAND/supervisor；`McpClientModule` 隐藏协议/transport。

### 1.2 未收敛的硬债

| # | 债 | 证据 | 影响 |
|---|---|---|---|
| F-1 | **`IZeroModule` 接口过宽**：10 个关注点（标识/生命周期/配置/FC 注册/权限/可用性/崩溃标记）塞一个接口 | `core/module-api/.../IZeroModule.kt` 全文 | 每个模块都得实现 `registerFunctions`/`requiredPermissions`/`checkAvailability` 即使不注册工具、不要权限；接口无法按需裁剪；新模态/新工具进来要反复改所有模块 |
| F-2 | **`services → core:module-manager` 反向依赖未解**：生产侧仍直接 `functionRegistry.register(...)` 往具体 `FunctionRegistryModule` 注册 | `framework/memory/.../MemoryModule.kt:112`（services/framework 模块径直注册） | P1-1 只拆了消费侧；注册中心仍是共享基础设施而非纯 app 编排层 |
| F-3 | **深模块协作者仍是具体类**：`ChatBotModule` 注入 `ContextBuilderModule`/`VisionModule`/`BudgetGuard`/`TokenBudgetAllocator`/`ConversationSummarizer` 为具体类 | `ChatBotModule.kt:50-61` | 实现深但协作面不可替换、难测；多模态替换/上下文策略替换需改 ChatBot 本身 |
| F-4 | **typed command 只覆盖 UI 入口**：`AutomationModule`/`SpeechSynthesisModule` 等内部编排仍走字符串 FC 名 | P1-2 收口自陈 | LLM 工具调用与模块内部编排未统一到 typed command |
| F-5 | **契约测试只覆盖 policy seam**：`IZeroModule`/生命周期/Bus 契约本身无测试 | 测试目录盘点 | 接口变更无回归网 |
| F-6 | **多表/先查后写仍缺 `@Transaction`** | §8.2 自陈"全库只有少量 @Transaction" | 进程内 Mutex 不能替代 SQLite 事务，不覆盖多进程 |

### 1.3 演进方向（优先级）

| 优先级 | 方向 | 说明 |
|---|---|---|
| P1 | **拆分 `IZeroModule`** | 按关注点拆为 `IModuleLifecycle` / `IFunctionProvider` / `IAvailabilityProvider` / `IConfigurable`；默认实现 trait 化，模块只实现关心的。这是后续所有演进的基座 |
| P1 | **注册侧 seam** | 抽 `FunctionRegistrar` 窄接口，`services` 依赖它而非具体 `FunctionRegistryModule`，闭合 F-2 |
| P2 | **深模块协作者接口化** | `ContextBuilder`/`VisionGateway`/`BudgetGuard` 抽 interface，ChatBot 注入接口；为多模态/上下文策略可替换铺路（与 §2 联动） |

| P2 | **补 `@Transaction`** | 按"先查后写"聚合事务逐项审计，与 §8.2 联动 |

**阶段定位**：框架化处于"骨架完整、深模块雏形具备、但核心接口与依赖方向尚未重构"的中段。建议在进入 Feature 专项前先做 F-1/F-2，否则多模态与工具扩张会反复踩这两条。

## 2. 多模态模型趋势下的框架跟进

### 2.1 当前实现：vision-poke → 文本注入（已实现）

`ChatBotModule.sendMessage` 对图片附件的处理（`ChatBotModule.kt:180-208`）：

1. 取附件 `base64Data`；
2. 调 `visionModule.analyzePoke()` 单独请求一次视觉模型，得到文字描述；
3. 把描述**写进用户消息正文**（`"[图片内容预分析]\n$description"` 拼入 `userMsg.content`）；
4. 聊天模型本身永远看不到原图，只看到另一模型转写的文字。

这是"文本为核心、多模态为工具"的字面落地。`modelSelector.select(setOf(ModelCapability.CHAT))`（`ChatBotModule.kt:222`）恒选文本模型；`FunctionResult.data` 为 `String`（`ChatBotModule.kt:376`），工具结果也只能是文本。

### 2.2 与趋势的张力（偏移）

代码注释自己暴露了症状：v6.8 修的"模型对图片失忆 + 每次带图请求打爆前缀缓存（hit 2%）"，本质是**文本注入在和架构对抗**——

- 图片信息有损：文字描述无法支持"图表左下角那个单元格"式的细节追问；
- 每轮 system 前缀变化打爆 prompt cache；
- 模型对图的"记忆"靠改写用户消息兜底，是症状治疗；
- 每来一个新模态（视频、流式音频、computer-use 截屏）就得再加一套 poke-and-inject hack。

原生多模态模型（支持 image_url / audio content block、computer-use 截屏）的趋势下，"poke → 文本 → 注入"是**把能力降级为工具**，而非利用模型原生能力。

### 2.3 跟进路径（渐进、不推翻现有）

| 优先级 | 方向 | 说明 |
|---|---|---|
| P1 | **引入 `ContentBlock` 抽象** | `ChatMessage.content` 现为 `String?`。OpenAI 兼容协议本就支持 multipart content。让 `ChatMessage` 携带 `List<ContentBlock>`（text/image_url/audio），`chatStream` 序列化。有能力的模型直接看原图，vision-poke 退为文本模型降级路径 |
| P1 | **以 `ModelCapability` 做路由轴** | `ModelSelector` 已按 capability 选模型（`ChatBotModule.kt:222`）。profile 声明 `IMAGE_INPUT` 则传原生图块，否则走 poke。廉价文本模型与 premium 多模态模型同框架共存 |
| P2 | **工具结果放开多模态** | `FunctionResult.data` 从 `String` 升级为可携带 `ContentBlock` 列表。截屏/图表工具可直接把图递回模型，不再 base64+描述有损转写 |
| P2 | **保留 vision-poke 为成本策略** | 对廉价文本模型预摘要仍有价值；从"唯一路径"降为"capability 路由下的一个策略"，与 `ToolContextSelector` 同属策略层 |
| P3 | **实时多模态会话边界显式化** | `LiveSessionService` 已是独立路径；明确"实时多模态会话"与"带附件文本对话"的 seam，避免两条路径耦合 |

**风险判断**：不做这些，框架会持续积累 v6.8 类补丁；每新增一个模态就多一次 poke-and-inject。做了，多模态成为对话一等公民而非外挂工具，且不破坏现有文本主链。

## 3. 记忆与知识库系统升级

### 3.1 记忆系统

**现状（核实）**：

- 3 层 tier（T0 临时 / T1 事件 / T2 事实），**正则规则分类**，零 LLM 成本（`MemoryModule.kt:553-596`）。代码自记两例误判修复（疑问句误入 T2、"我现在住在邵阳"漏判）。
- 混合检索：embedding 余弦（**Kotlin 层计算**，`getActiveWithEmbedding` 全量进内存逐条 cosine）+ 词法（keyword/bigram）→ RRF 融合 → `MemoryScoringEngine.rank`（`MemoryModule.kt:172-218, 303-313`）。
- `UserGraph` 三表 + 时间区间版本化属性 + 月级 0.05 置信衰减（`MemoryModule.kt:480-492`）；设计扎实。
- `pendingAiBuffer` **内存环形**（重启丢，`MemoryModule.kt:72, 270-274`；注释自承"对话历史仍在 Message 表可追溯"但提炼队列本身丢失）。
- Mutex 保护写入（`MemoryModule.kt:68, 77-79`）；T2 事实经 LLM 提炼（`extractFactWithLLM:393-409`，低频）。
- 记忆依赖**模型主动调 `memory_recall`** 工具触发检索。

**问题与演进方向**：

| 优先级 | 方向 | 证据/原因 |
|---|---|---|
| P0 | **向量检索出 Kotlin 内存层** | `embeddingCandidates` 全量进内存逐条 cosine（`MemoryModule.kt:303-313`），O(n) 且向量常驻。千条以下无碍，上万即崩。换 sqlite-vec/vss 扩展或轻量 ANN。**最紧的 scalability 债** |
| P1 | **tier 分类器换本地模型** | 正则模式跨语种/变体必脆，代码自记误判。本地 LLM 节点（RTX 5060 + llama.cpp + MiniCPM/Qwen，见环境资产）做 tier 分类，近零成本且泛化 |
| P1 | **记忆从"工具"转向"自动上下文"** | 依赖模型主动 `memory_recall`，小模型常不调导致"失忆"。contextBuilder 组 prompt 时按当前用户消息语义检索 top-K 直接注入 contextExtension；`ToolContextSelector` 意图匹配雏形可复用 |
| P2 | **pending buffer 持久化** | 加一张小队列表，重启不丢提炼队列 |
| P2 | **批量写 + 批量 embedding** | 在线写入逐条 insert + 逐条 schedule（backfill 已批 20，在线未批） |
| P3 | **图提取增量触发** | 当前 `pendingGraphCount` 阈值批触发；可考虑按记忆增量提取 |

### 3.2 知识库

**现状（核实）**：

- `KbDocEntity` / `KbChunkEntity` + `KbDao` 有 `@Transaction` + embedding BLOB + `embed_model` 换档防护（KA5）。
- 与 Memory **共用 `RetrievalKit` 底座**（cosine/RRF/bigram，`MemoryModule.kt:338-340` 注释），复用正确。
- `KbChunkEntity` 有 `heading_path` 字段，暗示部分结构意识。

**问题与演进方向**：

| 优先级 | 方向 | 说明 |
|---|---|---|
| P0 | **同样的向量库迁移** | KB 比 memory 更易涨大（文档），Kotlin-cosine 更先到顶 |
| P1 | **结构感知分块** | 按 markdown 标题/代码块/表格边界分块；`heading_path` 已有，分块器质量决定检索上限 |
| P1 | **加 reranker** | `MemoryScoringEngine.rank` 后接本地小模型 cross-encoder rerank；本地 LLM 节点可承担 |
| P2 | **embedding 换档再向量化管道** | `getWithoutEmbedding` 只抓 null 向量，不抓 model-mismatch；换 embedding 模型时旧 chunk 不会自动重向量化。补 model-mismatch 触发的 re-embed 路径 |
| P3 | **统一检索 API** | Memory/UserGraph/KB 各自独立查询是对的（§8.3 生命周期/真相/删除语义不同，**不合表**）；但应暴露统一检索接口让 contextBuilder 一次取齐，而非模型分别调三个工具 |

### 3.3 统一检索底座

`RetrievalKit` 已是 Memory 与 KB 共享底座——这是正确决策。建议把它显式升格为**整个检索域的 seam**（记忆/知识库/工具路由三者共用，见 §4.3），而非仅 Memory/KB 隐式复用。

## 4. 工具上下文膨胀：现有方案评估与下一步

### 4.1 现有三件套（P2-6，已实现）

- **`ToolSchemaBaselineTest`**：基线度量，当前 **4 工具、653 字符、723 字节、164 估算 token**。
- **`ToolContextSelector`**：按需装载。意图匹配（`contains` + 双字 bigram，`ToolContextSelector.kt:67-73`）+ 禁用模块过滤（读 `runtimeStates`）+ 默认 `includeAllOperational = true`（`ToolContextSelector.kt:20`）。
- **`ToolSchemaCompactor`**：无损紧凑，递归移除空 description / 空非语义扩展字段。

### 4.2 为什么不够（偏移）

三件套是**正确地基**，但对未来状态不足：

| # | 问题 | 证据 |
|---|---|---|
| T-1 | **Compactor 已到极限** | 当前压缩差值 = **0 字符**（基线自报）。写得好、没空字段可删。无损紧凑是一次性卫生，**不是扩展策略**；真正的膨胀是有意义的描述文本，无法无损压缩 |
| T-2 | **Selector 意图匹配太朴素** | `ToolContextSelector.kt:67-73` 是 `contains` + 双字 bigram。"帮我搜索天气"能命中 `web_search`，但抽象意图（"我有点冷" → 温控？）失效；大目录下 bigram 召回噪声大。**这是关键词匹配，不是语义路由** |
| T-3 | **默认仍全量** | `includeAllOperational = true` 默认；意图不命中时（通用助手大多数轮次）仍注入全部 operational 工具。**膨胀在常见情况下没被真正解决**。4 工具 ≈ 41 token/工具；50 工具 ≈ 2050 token、100 工具 ≈ 4100 token，每轮都付，即使本轮不需要工具 |

**一句话**：对当前 4 工具 164 token 是过度工程；对 50+ 工具不足以扩展。Compactor 已 delta=0（无损已尽），Selector 是 bigram 关键词匹配（不能 scale），默认全量（常见情况仍膨胀）。

### 4.3 真正的解锁（且底座已具备）

| 优先级 | 方向 | 说明 |
|---|---|---|
| P1 | **语义工具路由 = RAG-for-tools** | 工具目录就是另一个检索问题。embed 每个工具 description 一次，用户意图 embed 后检索 top-K 工具注入。**已有 `EmbeddingProvider` + `RetrievalKit` 底座可直接复用**；bigram matcher 是用错了工具的错配 |
| P1 | **分层命名空间** | `ModuleMetadata.category` 已存在但未用于工具选择。两级路由：先按域（system/media/communication/knowledge）筛，再按工具 |
| P2 | **轮间动态装载** | OpenAI spec 允许轮间增删 tools。第一轮可不注入工具让模型先表态，或用"tool_request"元工具按需展开。更激进但更省 |
| 已做对 | **工具结果体积控制** | `trimTurnTools` + `toolTrimChars`（`ChatBotModule.kt:526-546`）处理结果膨胀，与 schema 膨胀正交，方向正确，保持 |

**关键洞察**：工具膨胀、记忆检索、知识库检索在数学上是**同一类检索问题**——从候选集中按意图取 top-K。`RetrievalKit` 应升格为三域共享 seam，语义工具路由直接建在其上，而非让 `ToolContextSelector` 维护一套独立的 bigram 匹配。
